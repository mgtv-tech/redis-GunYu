# Redis-GunYu 改造实施计划（重排版）

## 一、改造目标

1. 先落地 **元数据 Redis Sentinel + Checkpoint 写入链路**，作为后续所有阶段的前置依赖。
2. 在不影响主数据链路（源端 -> 本地落地 -> 目标端）的前提下，完成 Input/Output 解耦。
3. 再实现 Input/Output 高可用与故障切换。
4. 最后实现按 Slot（16384）的 checkpoint，支持异构分片集群双向同步。
5. 增加前端 Web 管理平台，支持同步程序安装配置、多实例统一管理与已有实例纳管。

---

## 二、总体原则

- Checkpoint 采用双边界：`input_cp` 在 **meta.redis（Sentinel 托管）**，`output_cp` 在 **目标端 Redis**。
- 两类 checkpoint 严格命名隔离，禁止混用/复用 key。
- 本地落地（channel）继续作为数据缓冲与恢复介质。
- 阶段之间必须有明确依赖，不跳阶段。

#### 阶段2/3状态机分层口径（统一定义）

- **分层原则**：生命周期、Input角色、Output角色三层正交，不混用同一状态字段表达不同语义。
- **L1：Syncer生命周期状态（总控层）**
  - 状态：`ready_run` / `run` / `stop`（`pause` 预留）
  - 含义：描述“syncer主循环是否在运行”，不代表 Input/Output 的主备角色。
- **L2：Input HA角色状态（采集层）**
  - 状态：`leader` / `follower`
  - 语义：`leader` 负责源端采集并推进 `input_cp(meta.redis)`；`follower` 只读/待接管，接管后转为 `leader` 继续推进。
- **L3：Output HA角色状态（回放层）**
  - 状态：`leader(active)` / `follower(standby)` / `takeover(active)`
  - 语义：仅 active 侧回放数据并推进 `output_cp(目标端)`；standby 不执行回放写入。
- **PAUSED/RESUME 语义（当前口径）**
  - `PAUSED` 仅控制 Output 回放环节（等价 `outputPaused=true`），用于“暂停发送到目标端”。
  - Input 采集与本地落地不受影响，仍持续推进 `input_cp(meta.redis)`。
  - `RESUME` 仅恢复 Output 回放，不触发 Input 角色切换或生命周期重建。
- **验收要求**
  - 运行态与文档统一按“三层状态”描述，禁止将 `SyncerState` 误解释为 Input/Output 角色状态。
  - 所有暂停相关用例按“仅暂停Output、Input持续采集”进行验证与记录。

#### 任务4.4：源端 failover 局部重建（替代全局重启，工业级增强）
- **目标**：源端主从切换/拓扑抖动时，仅重建受影响 shard 的 Input 链路；其他 shard 与 Output 持续运行。
- **子任务4.4.1：触发面收敛（分类错误，不再一刀切）**
  - 将源端拓扑变化从“全局 `runWait.Close(ErrRestart)`”收敛为“按 input/shard 标记重建”。
  - 保留全局重启为兜底，仅用于不可恢复错误（协议损坏、关键元数据不一致、持续重试超阈）。
- **子任务4.4.2：局部重建执行器**
  - 在 `runCluster` 维持 shard 级生命周期控制：单 shard 退出后仅重建该 shard 的 `syncer`。
  - 重建时复用既有 checkpoint 语义：`input_cp(meta.redis)` 连续、`output_cp(目标端)` 不回退。
  - 与 `pause_all_outputs` 持久化状态联动：局部重建后自动恢复暂停意图。
- **子任务4.4.3：可观测与验收**
  - 新增（或补齐）“局部重建次数/耗时/影响分片”日志与指标。
  - 验收用例：单分片源端 failover 时，仅该分片出现短暂重建；其他分片 `State=run` 持续。
  - 通过标准：  
    - 无全局 `stop/restart`；  
    - 非故障分片无明显抖动；  
    - 故障分片在目标 RTO 内恢复并保持 checkpoint 单调。
- **当前进展（2026-03-06，第一轮落地）**：
  - 已改造 `runCluster`：源端角色探测异常、`role!=master`、campaign 抖动改为“本分片局部重试”，不再直接关闭全局 `runWait`。
  - 已改造 `checkTypology(watchIn)`：源端 master 地址变化/选中节点变化改为记录并由局部重建吸收，不触发全局重启。
  - 已补充运行中守护：`clusterTicker` 周期校验当前 input 是否仍为 master，若降为 slave 则触发 `ErrRestart` 走局部重建（不触发全局重启）。
  - 已补充重建重绑定：每轮局部重建前按最新拓扑刷新 `cfg.Input` 的 shard master 地址（按 slot 匹配），避免继续绑定旧 slave。
  - 已补充可观测指标：
    - `redisGunYu_syncer_source_local_rebuild_total{input,reason}`
    - `redisGunYu_syncer_source_local_rebuild_duration_ms{input,reason}`
    - 说明：`reason` 当前覆盖 `role_check_error`、`role_not_master`、`campaign_error`、`syncer_restart_error`、`master_rebind`、`ticker_role_not_master`。
  - 已保留全局兜底：`ErrCorrupted/ErrQuit` 等不可恢复错误仍可触发全局退出，避免静默坏状态扩散。
  - 已完成实测：对源端从节点执行 `CLUSTER FAILOVER TAKEOVER` 后，`18012/18013` 在 24s 观测窗口内均保持 `State=run`，未出现全局 `stop`。

**脚本 S4-6：源端/目标端 Redis 切换不影响同步（新增）**
- 目标：
  - 源端 Redis 拓扑切换（主从切换/slot owner 变更）后，Input 可自动续传，不中断长期同步；
  - 目标端 Redis 拓扑切换后，Output 可自动恢复写入，不出现不可恢复中断。
- 注入命令（示例）：
  - 源端切换：对源端集群对应主节点执行 `CLUSTER FAILOVER`（或等价主从切换操作）
  - 目标端切换：对目标端集群对应主节点执行 `CLUSTER FAILOVER`（或等价主从切换操作）
  - 若使用 Sentinel 托管 standalone，执行 `SENTINEL failover <masterName>`
- 观测重点：
  - 源端切换后：`RedisInput psync`/拓扑刷新日志连续，无长时间停滞，`input_cp(meta.redis)` 单调；
  - 目标端切换后：Output 重连/重试后恢复发送，`output_cp(目标端)` 单调，无不可恢复错误；
  - 切换前后：抽样 key 最终收敛，允许短窗口 at-least-once 重放，不允许长期缺失。
- 通过标准：
  - 源端切换与目标端切换分别通过；同步任务保持 `run`；
  - checkpoint 不回退（允许短窗口重复写但需可观测）；
  - 60s~120s 观测窗口内抽样一致性恢复。

**脚本 S4-7：PAUSED/RESUME（仅暂停Output，不影响Input）**
- 目标：
  - 验证 `PAUSED` 仅作用于 Output 回放，不中断 Input 采集与落地；
  - 验证 `RESUME` 后 Output 可从当前进度继续回放并追平积压。
- 注入步骤（建议持续写流量）：
  - 对目标任务执行暂停（仅 Output）：`PAUSED`
  - 保持 120s 持续写入样本数据（含 string/hash/zset）
  - 对目标任务执行恢复：`RESUME`
- 观测重点：
  - 暂停窗口内：`input_cp(meta.redis)` 持续前移，`output_cp(目标端)` 可短时停滞；
  - 暂停窗口内：允许 `lag_offset/lag_time` 增大，但 `syncer` 生命周期保持 `run`；
  - 恢复后：`output_cp` 重新前移并追平，`lag_offset/lag_time` 回落至常态区间。
- 通过标准：
  - 暂停期间 Input 无中断（`input_cp` 单调前进）；
  - 恢复后 Output 可追平（`output_cp` 继续单调前进，样本最终一致）；
  - 全程无不可恢复退出，且无“暂停导致角色错切换”现象。

**脚本 S4-8：源端局部重建一致性专项（新增）**
- 目标：
  - 验证“源端 failover -> 单分片局部重建”不会引入长期不一致；
  - 明确一致性语义：允许短窗口 at-least-once 重放，不允许长期缺失/回退。
- runid 收敛口径（新增）：
  - `T0(切换瞬间)`：允许旧/新 runid 混用（拓扑切换与连接重建窗口）；
  - `T1(兼容窗口)`：允许基于 `master_replid2` 继续 `PSYNC CONTINUE`，优先保持增量连续性；
  - `T2(收敛期)`：`input_cp/channel/output_cp` 进入新主路径并稳定单调，旧 runid 仅保留查询兜底。
- 样本设计（同时覆盖幂等/非幂等）：
  - 幂等：`SET stage4:s8:idem:<slotTag> v1 -> v2`
  - 非幂等：`INCR stage4:s8:nonidem:<slotTag>`
  - 分片覆盖：`low/mid/high` 各至少 1 组，执行前用 `CLUSTER KEYSLOT` 校验命中区间。
- 注入步骤：
  - 基线采样：记录源/目标端幂等值与非幂等计数、`/syncer/status`、`lag_offset/lag_valid`。
  - 在源端目标分片从节点执行：`CLUSTER FAILOVER TAKEOVER`（单分片注入）。
  - 注入后持续写入 60s，继续采样 120s。
- 观测重点：
  - 生命周期：非故障分片 `State=run` 持续，无全局 `stop/restart`；
  - 一致性：幂等样本最终收敛；非幂等样本允许小窗口重复但不可长期偏离；
  - 连续性：`input_cp/output_cp` 无长期停滞，`lag_valid=1` 时 lag 可回落。
  - runid 演进：允许 T1 窗口内沿旧 runid 增量；要求通过“先探测再切换”进入 T2（不要求切换后立即改新 runid）。
  - 可观测：`redisGunYu_syncer_source_local_rebuild_total{input,reason}` 在注入窗口出现增量。
- 通过标准：
  - 120s 窗口内，`low/mid/high` 幂等样本全部收敛；
  - 非幂等偏差在可接受阈值内（默认 `|A-B| <= 3`，超阈触发复核）；
  - 无全局重启，且无单分片长期卡死（`send_cmd=0` 持续 >5m）；
  - runid 切换原理：源端切换后先沿旧 `replid2` 保持增量同步；到收敛窗口（当前 `10s`）后，程序先探测 `PSYNC <newid> <knownOffset>` 是否可 `CONTINUE`；

  - 指标实现口径（方式2，默认 `meta.redis` 与目标端时钟一致）：
    - `redis_gunyu_output_checkpoint_lag_offset{input=...}`
    - `redis_gunyu_output_checkpoint_lag_time{input=...}`（单位：ns）
    - `redis_gunyu_output_checkpoint_lag_valid{input=...}`（1=有效，0=无效）
  - 有效门控（任一命中即 `lag_valid=0`，并将 lag 指标置为 `-1`）：
    - runId 为空/非法，或 `input_cp.runid != output_cp.runid`
    - 任一侧 checkpoint 不存在、读失败、字段非法（offset<0 或 mtime<=0）
    - 计算结果为负值（`lag_offset<0` 或 `lag_time<0`）
    - 同一 runId 下 checkpoint offset 回退（判定为无效窗口）
  - 告警建议（仅在 `lag_valid=1` 时生效）：
    - P3：`lag_offset > 10_000` 持续 1 分钟
    - P2：`lag_offset > 100_000` 或 `lag_time > 30s` 持续 3 分钟
    - P1：`lag_offset > 1_000_000` 或 `lag_time > 120s` 持续 5 分钟
  - Prometheus 告警规则样例（可直接落地，含 `lag_valid` 门控）：
```yaml

    rules:
      - alert: RedisGunYuLagP3

          redis_gunyu_output_checkpoint_lag_valid == 1

        for: 1m
        labels:
          severity: P3
        annotations:
          summary: "Redis-GunYu lag P3 on {{ $labels.input }}"
          description: "checkpoint lag_offset > 10000 for 1m"

      - alert: RedisGunYuLagP2
        expr: |

          description: "lag_offset > 100000 or lag_time > 30s for 3m"

      - alert: RedisGunYuLagP1
        expr: |
          redis_gunyu_output_checkpoint_lag_valid == 1
          and (
            redis_gunyu_output_checkpoint_lag_offset > 1000000
            or redis_gunyu_output_checkpoint_lag_time > 120000000000

        for: 5m
```

### 8.7 双Checkpoint边界与隐患防护（必须明确）

- [x] **命名与职责隔离**：`input_cp` 仅记录源端采集进度（存放于 `meta.redis`），`output_cp` 仅记录回放进度（存放于目标端）；两者使用不同前缀/命名空间，禁止复用key。
- [x] **ACK后前移规则**：`output_cp` 仅在目标端写入成功并收到确认后更新，禁止“先更新checkpoint后写数据”。
- [x] **回环过滤隔离**：A->B 与 B->A 使用独立过滤标记key，避免checkpoint相关命令被反向链路误处理。
- [ ] **落地文件保留保护**：AOF/RDB 清理策略必须受 `output lag` 保护，确保“checkpoint在、文件也在”，避免读取断档。
- [~] **拓扑变更连续性**：源端/目标端拓扑变化后，runId/replid 与 checkpoint 键选择规则保持连续，支持自动恢复与重试（目标端failover已优化为无全局重启，源端侧仍需细化局部重建）。
- [~] **降级与兜底策略**：当 `meta.redis` 或目标端checkpoint读取失败时，必须有可观测的降级策略（重试、回退安全点、告警），避免静默错位（已具备重试与告警基础，回退安全点策略待补）。

> 注：按当前设计，`input_cp(meta.redis)` 与 `output_cp(目标端)` 在命名隔离正确的前提下不会互相覆盖；主要风险不在“覆盖”，而在“语义混淆、更新时机、回环与清理策略”。
