# Redis-GunYu 改造实施计划（重排版）

## 一、改造目标

1. 先落地 **元数据 Redis Sentinel + Checkpoint 写入链路**，作为后续所有阶段的前置依赖。
2. 在不影响主数据链路（源端 -> 本地落地 -> 目标端）的前提下，完成 Input/Output 解耦。
3. 再实现 Input/Output 高可用与故障切换。
4. 最后实现按 Slot（16384）的 checkpoint，支持异构分片集群双向同步。

---

## 二、总体原则

- Checkpoint 采用双边界：`input_cp` 在 **meta.redis（Sentinel 托管）**，`output_cp` 在 **目标端 Redis**。
- 两类 checkpoint 严格命名隔离，禁止混用/复用 key。
- 本地落地（channel）继续作为数据缓冲与恢复介质。
- 阶段之间必须有明确依赖，不跳阶段。

**脚本 S4-2：网络分区（本机防火墙模拟）**
- 注入命令：
  - `powershell -Command "New-NetFirewallRule -DisplayName 'GY-DENY-18012-IN' -Direction Inbound -Action Block -LocalPort 18012 -Protocol TCP"`
  - `powershell -Command "New-NetFirewallRule -DisplayName 'GY-DENY-18012-OUT' -Direction Outbound -Action Block -RemotePort 18012 -Protocol TCP"`
- 恢复命令：
  - `powershell -Command "Remove-NetFirewallRule -DisplayName 'GY-DENY-18012-IN'"`
  - `powershell -Command "Remove-NetFirewallRule -DisplayName 'GY-DENY-18012-OUT'"`
- 观测重点：
  - 分区期间 follower 出现 `Unavailable/connection error`，随后重新选主并收敛。
- 通过标准：
  - 分区解除后角色稳定；checkpoint 连续；无长时间双主。

**脚本 S4-3：Sentinel 切主（meta.redis）**
- 注入命令：
  - `go run ./tools/redis_admin -addr 127.0.0.1:26379 -cmd SENTINEL -a1 failover -a2 mymaster`
  - 说明：当前本地 Sentinel 未启用 `requirepass`，不传 `-pass`；若启用鉴权再补 `-pass/-user`。
- 观测命令：
  - 日志查：`sentinel discovered master`、`sentinel connect success`
  - 运行态查：`/syncer/status` 持续 `run`
- 通过标准：
  - 切主后 checkpoint 读写不中断；实例不因 sentinel 切主退出。

**脚本 S4-4：目标端短暂不可用（仅 Output 压测）**

- 恢复命令：
  - `powershell -Command "1..6 | % { Remove-NetFirewallRule -DisplayName ('GY-DENY-800' + $_) }"`
- 观测重点：
  - Output 出现重试日志；Input 仍持续落地；恢复后 Output 从 checkpoint 继续回放。
- 通过标准：
  - 无不可恢复退出；恢复后延迟收敛，checkpoint 单调推进。

**脚本 S4-5：一致性抽样比对（最小闭环）**
- 样本写入（源端）：
  - `go run ./tools/redis_admin -cluster -addr 127.0.0.1:7001 -pass EPBQMMNnprXsXCZ6wsnZ -cmd SET -a1 stage4:key:1 -a2 v1`
  - `go run ./tools/redis_admin -cluster -addr 127.0.0.1:7001 -pass EPBQMMNnprXsXCZ6wsnZ -cmd HSET -a1 stage4:hash:1 -a2 f1 -a3 v1`
- 目标抽样：
  - `go run ./tools/redis_admin -cluster -addr 127.0.0.1:8001 -pass EPBQMMNnprXsXCZ6wsnZ -cmd GET -a1 stage4:key:1`
  - `go run ./tools/redis_admin -cluster -addr 127.0.0.1:8001 -pass EPBQMMNnprXsXCZ6wsnZ -cmd HGET -a1 stage4:hash:1 -a2 f1`
- 专项说明（7006/high 分片）：
  - 验证高分片时，样本 key 必须先确认 `slot ∈ [10923,16383]`，避免“写入命中其他分片”造成误判。
- 通过标准：
  - 故障前后抽样值一致；允许 at-least-once 下短窗口重复写，但不允许回退丢失。

**脚本 S4-6：源端/目标端 Redis 切换不影响同步（新增）**
- 目标：
  - 源端 Redis 拓扑切换（主从切换/slot owner 变更）后，Input 可自动续传，不中断长期同步；
  - 目标端 Redis 拓扑切换后，Output 可自动恢复写入，不出现不可恢复中断。
- 注入命令（示例）：
  - 源端切换：对源端集群对应主节点执行 `CLUSTER FAILOVER`（或等价主从切换操作）
  - 目标端切换：对目标端集群对应主节点执行 `CLUSTER FAILOVER`（或等价主从切换操作）
  - 若使用 Sentinel 托管 standalone，执行 `SENTINEL failover <masterName>`
- 观测重点：
  - 源端切换后：`RedisInput psync`/拓扑刷新日志连续，无长时间停滞，`input_cp(meta.redis)` 单调；
  - 目标端切换后：Output 重连/重试后恢复发送，`output_cp(目标端)` 单调，无不可恢复错误；
  - 切换前后：抽样 key 最终收敛，允许短窗口 at-least-once 重放，不允许长期缺失。
- 通过标准：
  - 源端切换与目标端切换分别通过；同步任务保持 `run`；
  - checkpoint 不回退（允许短窗口重复写但需可观测）；
  - 60s~120s 观测窗口内抽样一致性恢复。

## 八、工业级验收门槛

### 8.1 SLO 与恢复目标

- [ ] **可用性目标**：同步服务月度可用性 >= 99.9%
- [ ] **恢复时间目标（RTO）**：单节点故障后 30s 内恢复同步
- [ ] **数据丢失目标（RPO）**：进程异常重启场景 RPO <= 1s（按checkpoint刷新周期）
- [ ] **重复回放窗口**：故障切换后允许小窗口 at-least-once，窗口上限可观测且可告警

### 8.2 故障演练门槛（必须通过）

- [ ] **Sentinel切主演练**：主从切换后自动恢复 checkpoint 读写与同步
- [ ] **网络分区演练**：短时网络抖动/分区后无长时间卡死
- [ ] **目标端不可用演练**：目标Redis不可用后可重试并恢复，不出现不可恢复中断
- [ ] **进程反复重启演练**：连续重启后仍可按 checkpoint 续传
- [ ] **分离生命周期演练**：仅Output故障时，Input保持持续落地且不退出
- [ ] **恢复追平演练**：Output恢复后可自动追平积压并持续更新目标端checkpoint

### 8.3 数据一致性门槛

- [ ] **双向回环控制**：过滤策略稳定，无明显误过滤/漏过滤
- [ ] **偏移单调性**：checkpoint offset 单调递增（允许故障恢复回退窗口有记录）
- [ ] **抽样对账**：按库/slot抽样对账通过率 >= 99.99%
- [ ] **一致性报告**：每次发布后产出一致性验证报告

### 8.4 可观测性与告警门槛

- [ ] **核心指标齐全**：lag、checkpoint延迟、回放QPS、失败率、重试次数、切主耗时
- [ ] **告警分级**：P1/P2/P3 告警阈值、抑制与升级链路明确
- [ ] **日志可追踪**：按 taskId/runId/slot 可关联输入、回放、checkpoint 三段日志
- [ ] **审计可回放**：关键操作（切主、重试、回退）有审计记录

### 8.5 发布与回滚门槛

- [ ] **灰度发布能力**：支持按任务/实例灰度，支持快速回退
- [ ] **双栈兼容窗口**：etcd 与 meta.redis 迁移期间可灰度并行验证
- [ ] **回滚手册**：故障场景有标准回滚SOP，值班人员可执行
- [ ] **变更冻结机制**：重大活动期间具备冻结与快速止损机制

### 8.6 安全与合规门槛

- [ ] **访问控制**：元数据Redis启用ACL最小权限
- [ ] **传输安全**：生产环境支持TLS（按环境可配置）
- [ ] **密钥管理**：账号密码轮换机制与泄露应急预案
- [ ] **多租户隔离**：不同环境/任务 key namespace 强隔离

### 8.7 双Checkpoint边界与隐患防护（必须明确）

- [ ] **命名与职责隔离**：`input_cp` 仅记录源端采集进度（存放于 `meta.redis`），`output_cp` 仅记录回放进度（存放于目标端）；两者使用不同前缀/命名空间，禁止复用key。
- [ ] **ACK后前移规则**：`output_cp` 仅在目标端写入成功并收到确认后更新，禁止“先更新checkpoint后写数据”。
- [ ] **回环过滤隔离**：A->B 与 B->A 使用独立过滤标记key，避免checkpoint相关命令被反向链路误处理。
- [ ] **落地文件保留保护**：AOF/RDB 清理策略必须受 `output lag` 保护，确保“checkpoint在、文件也在”，避免读取断档。
- [ ] **拓扑变更连续性**：源端/目标端拓扑变化后，runId/replid 与 checkpoint 键选择规则保持连续，支持自动恢复与重试。
- [ ] **降级与兜底策略**：当 `meta.redis` 或目标端checkpoint读取失败时，必须有可观测的降级策略（重试、回退安全点、告警），避免静默错位。

> 注：按当前设计，`input_cp(meta.redis)` 与 `output_cp(目标端)` 在命名隔离正确的前提下不会互相覆盖；主要风险不在“覆盖”，而在“语义混淆、更新时机、回环与清理策略”。
