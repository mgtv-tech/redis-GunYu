## 1. Overview

`bisync` is the bidirectional synchronization feature in `redis-GunYu`. It runs two sync links between two Redis deployments: A -> B and B -> A.

Its main goals are:

- synchronize business writes from each side to the other side
- suppress mirrored writes generated by GunYu itself, so an A -> B replay is not replayed back by B -> A
- resume from reliable recovery metadata after syncer restart, Redis failover, or target cluster topology changes

The current implementation supports:

- Redis standalone bidirectional sync
- Redis cluster bidirectional sync
- AOF incremental replay
- RDB full sync replay
- sync replay mode
- pipeline replay mode
- replay-unit-level retry on target `MOVED` / `ASK` redirects

The current implementation wraps each replay unit in a real Redis `MULTI/EXEC` transaction. The transaction writes:

- a short-lived marker for reverse-link mirrored transaction suppression
- business commands
- bisync recovery metadata

Design selection details are in [bisync_scheme_selection_en.md](./bisync_scheme_selection_en.md). Implementation details are in [bisync_scheme1_impl_en.md](./bisync_scheme1_impl_en.md). Chinese versions are [bisync.md](./bisync.md), [bisync_scheme_selection.md](./bisync_scheme_selection.md), and [bisync_scheme1_impl.md](./bisync_scheme1_impl.md). Checkpoint key details are currently documented in [checkpoint_zh.md](./checkpoint_zh.md).

## 2. Suitable Use Cases

Bisync is suitable when:

- two Redis deployments need data to flow in both directions
- the business can accept eventual consistency rather than strong multi-master consistency
- both sides do not frequently write the same keys at the same time
- the business has defined conflict semantics for same-key writes from both sides
- synchronization scope can be controlled by GunYu filters

Bisync is not suitable as-is when:

- the system requires strong consistency, multi-master conflict detection, or CRDT semantics
- both sides heavily write the same key set and cannot accept overwrite, additive effects, or ordering differences
- Redis module commands are core traffic but have not been verified with keyspec and regression tests
- business traffic depends on custom commands whose keys cannot be parsed by GunYu

## 3. Configuration

Bisync must be configured on both sync links. In other words, start one syncer for A -> B and another syncer for B -> A.

Key options are under `output.replay`:

```yaml
output:
  redis:
    # Fill in the target Redis configuration as usual.
  replay:
    resumeFromBreakPoint: true
    replayTransaction: true
    bisyncEnabled: true
    mode: sync
    keyExists: replace
```

| Option | Recommended value | Description |
| --- | --- | --- |
| `bisyncEnabled` | `true` | The only explicit bisync switch. Default is `false`. |
| `replayTransaction` | `true` | Recommended. It is not the bisync switch, but still controls the normal replay path. |
| `mode` | `sync` / `pipeline` | AOF replay execution semantics. In non-bisync replay, `pipeline` replaces the old pipeline mode. |
| `resumeFromBreakPoint` | `true` | Recommended for breakpoint resume. |
| `keyExists` | `replace` / `ignore` / `error` | Behavior when target keys already exist during RDB full sync. |

`mode` has two values:

- `sync`: send one replay unit and wait for its full reply before sending the next; recovery uses slot-local `latest` checkpoints
- `pipeline`: send and receive run in different goroutines, but replies and checkpoints are handled in send order; recovery uses `commit journal + frontier`

Do not validate only one mode and then deploy another. `sync` and `pipeline` use different recovery surfaces, and both execution semantics must be tested separately.
If your workload is highly sensitive to bidirectional consistency, prefer `sync`. The current `pipeline` mode can still hit data-consistency issues in extreme scenarios and should not be treated as a strict-consistency mode.

## 4. How It Works

Bisync splits the source replication stream into replay units:

- normal command: one command becomes one replay unit
- source transaction: the whole `MULTI ... EXEC` becomes one replay unit
- RDB entry: replay units are built per key or split-key segment

Each replay unit is committed to the target Redis as a real transaction:

```redis
MULTI
SET redis-gunyu-bisync:<checkpointName>:marker:{slotTag} <marker> PX <ttl>
... business commands ...
HSET/ZADD ... bisync metadata ...
EXEC
```

When the reverse link parses AOF and sees a valid marker inside a transaction, it suppresses the whole mirrored transaction and does not replay it back to the original side.

In cluster mode, every replay unit must prove that all business keys belong to one slot. In standalone mode, GunYu uses synthetic slot `0`, so a transaction may contain keys from any hash slot.

## 5. Recovery Metadata

Bisync still uses the source `runId + offset` as the replication stream recovery axis, but bisync metadata is stored under a stable `checkpointName` namespace.

Common keys:

| Key | Purpose |
| --- | --- |
| `redis-gunyu-checkpoint-bisync:<id>` | bisync namespace root |
| `redis-gunyu-checkpoint-bisync:<id>:frontier` | global contiguous recovery point in `pipeline` mode |
| `redis-gunyu-bisync:<checkpointName>:marker:{slotTag}` | mirrored transaction suppression marker |
| `redis-gunyu-bisync:<checkpointName>:latest:{slotTag}` | slot-local recovery point in `sync` mode |
| `redis-gunyu-bisync:<checkpointName>:commit:{slotTag}:<unitSeq>` | commit journal in `pipeline` mode |
| `redis-gunyu-bisync:<checkpointName>:index:{slotTag}` | commit journal index in `pipeline` mode |

These keys are GunYu control-plane keys. Business clients must not read, write, migrate, or delete them.

## 6. Unsupported or Not Recommended Commands

### 6.1 Module Command Support Boundary

Static keyspec coverage has been added for selected RedisJSON, RedisBloom, and RediSearch commands, and their key extraction has been checked against Redis Stack module instances with `COMMAND GETKEYS`:

| Module | Commands |
| --- | --- |
| RedisJSON | `JSON.SET`, `JSON.DEL`, `JSON.MSET` |
| RedisBloom | `BF.ADD`, `CMS.MERGE`, `TDIGEST.MERGE`, `TOPK.ADD` |
| RediSearch | `FT.CREATE`, `FT.SEARCH`, `FT.DROPINDEX` |

This means bisync cluster routing can prove the key set for these commands; it does not mean Redis Modules are fully supported. Before sending module commands through a production bisync link, all of the following still need to hold:

- the target Redis loads the corresponding module
- `COMMAND GETKEYS` or static keyspec can return a provable key set
- strict routing can prove whether the command is single-slot in cluster mode
- the command is covered by `tests/bisync/run_category4.sh` or additional stable samples

For RDB full sync, keyspace module objects use the opaque `RESTORE` path. The target Redis must load compatible modules and `replayRdbEnableRestore: true` must stay enabled. Real Redis Stack validation covers RedisJSON and RedisBloom keyspace data types. RediSearch indexes and other `MODULE_AUX` global module metadata are not supported yet. By default, `replay.moduleAuxPolicy: fail` stops RDB replay before checkpointing when such metadata is found. Set `replay.moduleAuxPolicy: skip` only when those indexes are known to be rebuilt through incremental module commands or an external procedure.

### 6.2 Commands Whose Keys Cannot Be Parsed

The cluster bisync path depends on the real key set. If static keyspec does not cover a command and target Redis `COMMAND GETKEYS` cannot parse it, the syncer fails stop instead of best-effort replaying it.

Add keyspec coverage or verify it with `keyspec_verify` before enabling such commands.

### 6.3 Cross-Slot Transactions in Cluster Mode

In cluster mode, one replay unit must bind to one slot. A source transaction that spans multiple slots cannot be wrapped as one real target transaction.

The current behavior is conservative failure, not partial replay.

### 6.4 Limited Partial Projection

When filters keep only part of a transaction, only a small set of commands currently supports safe partial projection, such as:

- `MSET`
- `DEL`
- `UNLINK`

Other multi-key commands are handled conservatively. If safety cannot be proven, the syncer fails or rejects the projection.

## 7. Current Limitations

1. Bisync does not resolve business conflicts.

   If both sides write the same key, GunYu does not decide which value is correct. The final result depends on Redis command semantics, replication order, and recovery behavior. Non-idempotent commands such as `INCR`, `LPUSH`, and `XADD` require extra business review.

2. `pipeline` recovery does not precisely skip every committed unit.

   `pipeline` mode rebuilds the contiguous committed prefix from `frontier + commit journal`. If a crash leaves a gap after the frontier, units committed after the gap may still be replayed again after restart. The current semantic is recovery from the last contiguous committed point.

   In other words, under extreme failures, abnormal exits, or recovery windows, `pipeline` cannot guarantee strict data consistency. If your business cannot accept that risk, use `sync` or prepare extra reconciliation and repair steps before production rollout.

3. RDB replay does not provide per-key authoritative recovery points.

   The RDB bisync path provides mirrored-write suppression and full sync replay, but authoritative recovery still relies on the full-RDB checkpoint barrier.

4. Cluster-global objects still have boundaries.

   Non-key-based global opcodes such as `FUNCTION RESTORE` cannot be fully modeled as slot-local real transactions and must be managed by current special cases and regression results.

5. Severe topology instability is handled by fail-stop.

   Replay-unit-level retry on `MOVED` / `ASK` is supported, but if the target cluster keeps redirecting or remains unstable, the syncer stops instead of degrading to weak mode.

6. Redis version compatibility must be validated against the production version.

   Pay special attention to RDB format, keyspec, module commands, and `COMMAND GETKEYS` behavior.

## 8. Operational Notes

- Deploy both A -> B and B -> A links, with `bisyncEnabled: true` on both sides.
- Do not use `replayTransaction` as the bisync switch. Bisync is controlled only by `bisyncEnabled`.
- Do not manually delete or modify `redis-gunyu-bisync:*` and `redis-gunyu-checkpoint-bisync:*` keys.
- Do not use `redis-gunyu-bisync:` or `redis-gunyu-checkpoint-bisync:` as business key prefixes.
- In cluster mode, business transactions should use hash tags to stay in one slot.
- Start rollout with a limited business prefix or slot range.
- Define same-key write conflict semantics before rollout.
- Validate recovery, failover, and soak behavior before enabling `pipeline` mode.
- Re-run category4 and convergence tests after changing filters.

## 10. Observability and Troubleshooting

Check syncer status through the HTTP API:

```bash
curl http://127.0.0.1:<http-port>/syncer/status
```

Bisync-related metrics include:

| Metric | Meaning |
| --- | --- |
| `bisync_unit_build` | replay unit build count |
| `bisync_txn_commit` | bisync transaction commit count |
| `bisync_single_slot_fail` | single-slot validation failure count |
| `bisync_txn_suppress` | mirrored transaction suppression count |
| `bisync_frontier_seq` | `pipeline` frontier sequence |
| `bisync_frontier_offset` | `pipeline` frontier offset |
| `bisync_frontier_rebuild_seconds` | frontier rebuild duration |
| `bisync_commit_backlog` | `pipeline` commit backlog |
| `bisync_commit_gc` | commit journal GC count |

Watch for:

- whether `bisync_txn_commit` keeps increasing
- whether `bisync_txn_suppress` confirms mirrored transactions are being suppressed
- whether `bisync_single_slot_fail` increases
- whether `bisync_commit_backlog` stays high under sustained load
- repeated `MOVED` / `ASK`, frontier rebuild, journal gap, or strict routing failures in syncer logs

## 11. Release Recommendation

Recommended rollout steps:

1. Run unit tests and category1 to category5 plus category8 against the production Redis version.
2. Run category9 durability tiers for `sync` and `pipeline` modes.
3. Start canary rollout by business prefix or slot range, with controlled initial write volume.
4. Watch the status API, bisync metrics, Redis resources, and data comparison results.
5. Keep a rollback plan that can quickly disable `bisyncEnabled` or stop the reverse link.

Production acceptance criteria:

- business keys converge on both sides
- the intended `sync` or `pipeline` mode has been validated
- failover, syncer restart, and offline recovery still converge
- commit journal does not accumulate abnormally
- goroutine count, RSS, storer directory size, and Redis memory do not grow abnormally
- business traffic does not contain unsupported or unverified commands
